# Binance USD-M Safety Bot

## Risk warning

This is not a profit machine. It is a safety-first automation scaffold for Binance USD-M Futures. Futures can lose money quickly, and a 10% account risk per trade with leverage up to 5x is aggressive. Mainnet trading is blocked by default, every trade requires stop-loss and take-profit, and the project starts in `DRY_RUN`.

No strategy here guarantees profit. You must validate data quality, exchange behavior, fees, funding, latency, slippage, and backtest results before any live use.

## Parameter analysis

Your requested `risk_per_trade_pct: 0.10` means a sequence of losses can damage the account very quickly:

- 3 losses: about -27.1% before extra costs if size is recalculated after each loss.
- 5 losses: about -40.9%.
- 10 losses: about -65.1%.

The system therefore marks this as aggressive, sends risk warnings, enforces daily-loss and cooldown rules, and calculates size from stop distance rather than from leverage alone.

The starting deposit is defined as `100000` KZT, but Binance USD-M Futures trade with USDT margin. The bot will not guess a conversion rate. Set either `STARTING_DEPOSIT_USDT` or `MANUAL_TENGE_USDT_RATE` in `.env` for backtest/paper balances.

## Official API references used

- Binance USD-M Futures general info: mainnet REST `https://fapi.binance.com`, testnet REST `https://demo-fapi.binance.com`.
- Binance exchange information: `GET /fapi/v1/exchangeInfo`.
- Binance new order: `POST /fapi/v1/order`.
- Binance position risk v3: `GET /fapi/v3/positionRisk`.
- CoinGecko market cap source: `GET /api/v3/coins/markets`.

## Safe guardrails

- `MAINNET_LIVE` is disabled unless `safety.enable_mainnet_live: true` and the exact confirmation phrase is set.
- Mainnet also requires `data/production_unlock.json` with human approval plus backtest/paper approval flags, and `risk_per_trade_pct` must be no higher than `safety.max_mainnet_risk_per_trade_pct`.
- `TESTNET_LIVE` uses Binance Futures demo/testnet base URL.
- `DRY_RUN`, `PAPER_TRADING`, and `BACKTEST` never send live exchange orders.
- Stop-loss and take-profit are mandatory.
- New entries are blocked per symbol, not globally. BTC can be open while ETH/SOL are evaluated, but the portfolio gate enforces max concurrent positions, total risk, margin usage, and correlated-group risk.
- BTC 4h market filter blocks long entries when BTC has fallen more than the configured threshold over the latest 4h candle.
- UTC session filter blocks configured low-quality hours by default (`00:00-07:59 UTC`) until self-learning proves otherwise.
- Position size is calculated from entry-to-stop distance plus estimated fee, slippage, and funding buffer.
- Base risk is now 2% per trade. Fractional Kelly can adapt it from recent R-multiples, but it is capped between 0.5% and 3% by default.
- Partial take-profit ladder is generated by default: TP1/TP2/TP3, with TP1 moving the stop to breakeven and TP2 enabling trailing logic.
- Daily loss limit and losing-streak cooldown stop new entries.
- Max leverage is capped at 5.
- Live mode can require liquidation-price validation.
- Emergency stop can be activated from CLI, dashboard, or by creating `data/emergency_stop.flag`.
- Live reconciliation checks for active positions without stop orders, positions without take-profit orders, and orphan reduce-only orders.
- Martingale, grid without stops, revenge trading, and increasing risk after losses are not implemented.

## Architecture

- `data_provider`: Binance REST client, market candles, funding, open interest, spread, volume, CoinGecko top market-cap data.
- `market_universe`: dynamic top-10 selection and Binance USD-M Futures availability/liquidity filtering.
- `strategy_engine`: multi-timeframe EMA/RSI/ATR/volume/high-low structure signal generation.
- `market_regime_detector`: trend/range/volatility/momentum classification.
- `style_selector`: scalping/intraday/swing/no-trade selection.
- `risk_manager`: size, leverage, stop/take-profit validation, daily loss, cooldown, liquidation buffer.
- `trade_manager`: TP ladder, breakeven, trailing-stop planning and post-entry protection hooks.
- `order_manager`: dry-run, paper, gated live order flow, close-all SL, partial TP orders, fill verification, defensive cleanup.
- `position_manager`: per-symbol active-position tracking, manual/external position adoption, repeat-entry prevention.
- `trade_manager.supervisor`: Binance user-data stream listener. On `ORDER_TRADE_UPDATE` FILLED for TP1 it moves SL to breakeven; on TP2 it activates trailing stop.
- `trade_manager.supervisor`: handles `PARTIALLY_FILLED`, `FILLED`, stop/trailing fills, `ACCOUNT_UPDATE`, margin-call events, liquidation/ADL client IDs, and manual/external intervention.
- `execution`: REST reconciliation for partial fills, reduceOnly issues, missing protection, and orphan orders; this is only the backup path when the websocket is stale/disconnected.
- `backtester`: historical candle simulation with costs.
- `paper_trader`: local no-order execution model.
- `telegram_notifier`: operational and risk notifications.
- `web_dashboard`: FastAPI dashboard and emergency stop.
- `cli`: Typer commands for operations and checks.
- `logger`: standard logging setup.
- `database`: SQLite storage with a path that can later be replaced by PostgreSQL-oriented repository code.
- `analytics`: winrate, expectancy, R-multiple, profit factor, drawdown snapshots.
- `ml`: offline model hook. ML is disabled by default and cannot train online in live mode.

## Trading logic

The strategy reads 4h, 1h, and 15m candles together:

- 4h: global direction and market regime.
- 1h: market structure confirmation.
- 15m: entry timing.

Base indicators:

- EMA 20, EMA 50, EMA 200.
- RSI.
- ATR and ATR percent.
- Volume ratio versus rolling average.
- Recent high/low structure.
- Optional funding filter.
- Optional open-interest filter placeholder.
- Order book imbalance.
- Taker buy/sell ratio as a CVD-style proxy.
- Open-interest change filter.
- Liquidity sweep confirmation.
- Absorption wick/body logic.
- Aggressive buyer/seller delta.
- Structure-break confirmation.
- Liquidation-cluster filter placeholder, disabled until a reliable data source is wired.

Strategies:

- `TREND_FOLLOWING`: the original multi-timeframe EMA/RSI/ATR/order-flow strategy.
- `MEAN_REVERSION`: counter-trend strategy for exhaustion/range conditions. It enters against extreme 4h EMA200 deviation when deviation exceeds configured ATR multiples and RSI is oversold/overbought.

Market filters:

- `btc_4h_drop_filter_enabled`: blocks long entries if BTC 4h change is worse than `btc_4h_max_drop_pct`.
- `utc_session_filter_enabled`: blocks configured UTC hours.
- `use_self_learning_filters`: applies learned bad symbol/hour, ATR, and RSI buckets after enough history is collected.

## User Data Stream

Live modes require a healthy Binance USD-M user-data stream by default:

```yaml
trade_management:
  user_stream_required_for_live: true
  rest_reconciliation_when_stale: true
```

The bot starts `POST /fapi/v1/listenKey`, connects to `wss://.../ws/{listenKey}`, keeps it alive, and treats REST reconciliation as a backup. New entries are blocked if the user stream is disconnected.

Events handled:

- `ORDER_TRADE_UPDATE`: partial fills, TP fills, stop/trailing fills, liquidation/ADL order IDs.
- `ACCOUNT_UPDATE`: balance/position changes and manual/external positions.
- `MARGIN_CALL`: immediate risk warning.
- `CONDITIONAL_ORDER_TRIGGER_REJECT`: risk warning and reconciliation.

## Self-Learning

The analytics layer now generates concrete post-trade recommendations:

```bash
trading-bot self-learning
trading-bot ml-retrain
```

It segments trades by symbol, symbol+hour UTC, ATR bucket, RSI bucket, style, and edge condition. Example outputs include:

- Avoid/down-weight `SOLUSDT@2UTC` if expectancy is negative.
- Avoid ATR buckets such as `2.0-2.4%` if R expectancy is poor.
- Avoid RSI buckets such as `58-62` unless stronger edge confirmation is present.
- Lower or remove an edge condition if its trade sample underperforms.

The ML module is still intentionally offline and review-gated: it can retrain a lightweight logistic filter and report feature importance, but it does not mutate live thresholds automatically.

Style selection:

- Scalping: high volume, tight spread, elevated short-term volume, impulse-friendly volatility.
- Intraday: confirmed trend without extreme 4h displacement.
- Swing: strong 4h trend/structure and acceptable volatility.
- No trade: unclear regime, excessive spread, missing liquidity, incomplete SL/TP, bad backtest gate, or risk limits.

## Mainnet unlock

Mainnet requires all conditions below:

```yaml
mode: MAINNET_LIVE
safety:
  enable_mainnet_live: true
  mainnet_confirmation: "I_UNDERSTAND_MAINNET_RISK"
  max_mainnet_risk_per_trade_pct: 0.02
risk:
  risk_per_trade_pct: 0.01
```

It also requires valid `BINANCE_API_KEY` / `BINANCE_API_SECRET` in `.env` and a deliberate production unlock file:

```bash
cp data/production_unlock.example.json data/production_unlock.json
```

Edit the JSON only after documented backtest, paper-trading, and testnet review. If `backtest_approved`, `paper_trading_approved`, or `human_approved_by` are missing, the app refuses `MAINNET_LIVE`.

## PostgreSQL

SQLite is fine for research and single-process testnet use. For serious live deployment, set:

```yaml
database:
  url: "postgresql+asyncpg://bot:password@postgres:5432/trading"
```

and install:

```bash
pip install -e ".[postgres]"
```
